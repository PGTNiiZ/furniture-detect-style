## E: integrity blocker

E: reported exFAT, 134,213,533,696 bytes capacity and 123,003,731,968 bytes free before the copy; C: had only about 181 MB free. The copied `E:\furniture-data\archives\furniture_dataset.zip` is **not usable**: source `D:\Download\furniture_dataset.zip` had SHA-256 `dce23f8f54b1317d31805564a4d58ab0eff2ed3ce00e06656df188440563f79a`, while the E: copy read as `e88c5ae9e7eaf019f47fc05444d7f88ac97384e77ba212cdb3ead60ba076190e`. The source starts with a ZIP local-header signature; a later read of the E: copy began with `ff` bytes and failed ZIP parsing. Windows reported the E: **volume** health as `Warning`, although its disk health was `Healthy`. This does not establish the underlying hardware cause. Do not trust files written to E: until the drive/connection is independently diagnosed and a subsequent full-file checksum and ZIP validation pass. No formatting or deletion was performed. Both copies remain in place. An existing `D:\Download\Unconfirmed 553312.crdownload` was not treated as a complete archive or removed.

Automatic approval review rejected the combined command that would prepare directories and launch background downloads. The directories and a separate copy from an existing local ZIP were subsequently made, but the large archive was not downloaded. The remote large ZIP was inspected only with HTTP byte-range reads; this is metadata inspection, not local data access or training.

The two advertised ZIPs have 389,538,088 and 42,671,832,118 compressed bytes. Their outer central directories report 387,380,896 and 44,741,168,881 uncompressed bytes respectively. All four together total about 88.19 GB; allowing 20% adds about 17.64 GB, or 105.83 GB before a cache allowance and before extracting nested archives. The filesystem's free-space figure cannot establish reliability or prove all nested extraction would fit.

## Small archive: verified manifest content

The existing D: ZIP contains 25,194 entries classified as files: 25,173 image-extension files and 21 others, including eight report PNGs. Manifest rows: train 7,650, validation 1,350, real-source test 865, and train_aug 22,950. The bundled README says train_aug includes the original train rows plus 15,300 augmented copies; do not treat those copies as independent photographs. Its `labels.json` declares four types and 34 styles. Its preparation summary says 135 of 1,000 source test rows were excluded, predominantly because styles were not in the training vocabulary. It includes an alias mapping and source script, which must not be silently adopted as the new protocol.

The bundled README identifies `filnow/furniture-synthetic-dataset` as the source. Its 9,000 train images are described as generated and the 1,000 original test images as real; the large archive's source card states that test annotations were produced with Qwen2 VL 72B. They are source annotations, not verified expert ground truth. The small archive preparation script assigns `src_index` by reading parquet rows but does not establish a pinned revision in this audit.

Comparing those indices with v2 manifests found 1,098 small-train / v2-validation candidates and 954 small-train / v2-synthetic-test candidates. Of these, 1,041 and 894 respectively also have identical type and style strings. This is a **candidate** comparison, not verified image identity: confirm source revision/order, image identity, exclusions, and near duplicates before reuse. See `artifacts/small-v2-index-overlap-candidates.csv` and the reproducible summary. Do not train on these rows and then claim an uncontaminated evaluation on v2 holdouts.

Per-class counts, actual columns, prepared aliases and source scripts are in `artifacts/small-dataset-manifests-local.json`. No class mapping was accepted for a new snapshot, and no changed synthetic or real test was opened for model selection.

## Large archive: read-only inventory

Outer ZIP central-directory inspection reported 638,840 non-directory files, including 633,752 files with image extensions and 5,088 others. These counts include plots, alternate copies, and several nested archives, and are **not** a count of independent labeled source images. Sources identified in paths include Amazon-Berkeley-Objects, iMaterialist-Furniture-2018, DeepFurniture, Pix3D, HomeObjects-3K, IKEA-Dataset, Darebal_furniture-catalog and Furniture-Synthetic-Dataset. Full inventory and selected metadata are `artifacts/drive-archive-inventory.jsonl` and `artifacts/drive-source-annotations.json`.

HomeObjects-3K includes YOLO-style text labels and a YAML mapping with bed, sofa, chair and table plus eight other object categories; its own YAML describes 2,285 train and 404 validation images, which still require verification against files, scene/source independence, licensing and annotation quality. DeepFurniture category and metadata files exist, but its bundled dataset info literally has placeholder citation and license text. An Amazon-Berkeley-Objects CC-BY-4.0 license file and the synthetic dataset card declaring Apache-2.0 are present; this does not establish permissions for every source or downstream use. The large archive includes synthetic parquet data and a cache tree named with v2's source revision, but this alone does not establish identity of every image. Category/style coverage, missing labels, object counts, bounding-box quality, duplicate relationships across archives and source-by-source terms remain unverified.

## Loader feasibility and next steps

`artifacts/benchmark_flash_zip.py` is an isolated read-only feasibility probe, not integration into the training pipeline. It opens one ZIP handle per spawned worker, reads individual records lazily, uses existing preprocessing, checks sample uniqueness and fails on corrupt images. It has no disk cache or masked loss. It is not approved for a new training snapshot. Its D: results, if present, are loader-only timings on the first 128 existing train records with no controlled cold cache; RAM is parent-process peak only and excludes worker memory. They do not measure E: or training throughput. The E: run failed on ZIP corruption and produced no valid throughput result.

On D:, batch size 16 and 128 rows, both workers=0 and workers=2 yielded exactly 128 distinct IDs in each of two epochs with no reported image errors. The first/second epoch took 1.11/0.53 seconds with zero workers and 19.85/0.37 seconds with two; worker startup and uncontrolled Windows cache make these preliminary figures unsuitable for choosing E: settings. No GPU work was performed by this probe.

After the storage issue is resolved, obtain a checksum-verified local copy of each archive on a reliable data drive, audit exact and near duplicates against v2 holdouts, and inspect annotations and source terms before creating a separate immutable snapshot with train-only class mapping. Then integrate the reader and, only if category-only labels are actually used, masked loss with valid-label normalization and tests. Benchmark loader plus training with batch/worker settings, full process RAM/VRAM, error logs and cache bounds; perform a short pilot only after the audit. A comparison of v2 with v2 plus audited new images requires the same uncontaminated evaluation set and must report optimizer steps and compute. Existing augmentation, robustness and detector workflows remain separate and unchanged.
